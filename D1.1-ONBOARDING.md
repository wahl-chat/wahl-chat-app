# ONBOARDING — Data Ingestion (wahl.chat V2)

> **This is a proposed starting point, not a finished spec.** It's an initial design to give us a coherent, shared data body that everyone can build against in parallel. I think it works well but  fully expect that as each of you gets into a real source, some of it will need to bend. Treat the shapes and rules below as **defaults to start from and push back on**, not laws. If a source doesn't fit, that's a signal worth raising -> flag it and we adjust the contract together.

---

## 1. Mental model: how I've shaped the data layer (so far)

The idea: **one corpus, grouped by party, scoped by election at query time.** A single Qdrant collection per environment - dev (`wahlchat_chunks_dev`)/ prod - holds *every* source for *every* election, rather than splitting per election.

- **Partition key = `party_id`** -> it's the Qdrant tenant key (`is_tenant=True`), so a party's vectors co-locate. Queries filter by `party_id`.
- **Election scoping = query-time filter** on `region` + `region_path` (MatchAny). A chunk tagged `region="DE"` can be reused by every election whose path includes DE. You tag the chunk; the query does the matching.
- **Source filtering = `source_type` + `authority_tier`** payload indexes (e.g. only `vote_record`, only `authoritative`).

The thinking behind one-collection-by-party: it avoids duplicating national content per election and keeps cross-election queries cheap. But it's a hypothesis, if a source makes this awkward, let's talk.

**The working assumption is that every corpus source normalizes to the same shape** — `SourceItemRecord` — whether you scrape HTML, hit a JSON API or parse a PDF. The only per-source variation is the `source_type` / `authority_tier` tags. (Derived/external sources like pledges are the deliberate exception: Firestore-only `PledgeRecord`s, never embedded — the PledgeTracker path.) **How well this "one shape fits all" assumption holds is one of the main things this sprint will tell us** (see section 6).

### The three stores
| Store | Holds | Written by |
|-------|-------|-----------|
| **Qdrant** (`wahlchat_chunks_dev`) | the searchable corpus: 3072-dim vectors + `ChunkRecord` payload | the **embedding worker** (not your connector) |
| **Firestore** | `source_items/`, `ingestion_watermarks/`, `pledges/`, matcher collections (`questions`, `claims`, `topics`, …), + V1 `contexts/` | your connector (`source_items`, watermark) |
| **GCS** (fake-gcs locally) | verbatim original documents | your connector (`store_original()` → `gs://` ref) |

### The two key records (full field list in `CONTRACT.md`)
- **`SourceItemRecord`** → `source_items/{source_item_id}`. One ingested source. Note it carries **no body field** — the text lives in GCS and becomes chunks later, so "what counts as one source item" is a *keying choice you control*, not something the schema forces (this matters — see §6). Fields you'd typically set in `normalize()`: `source_type`, `external_id`, `party_id`, `region` + `region_path`, `authority_tier`, `publish_date`, `storage_ref`. The pipeline manages `vector_status` / `chunk_count`.
- **`ChunkRecord`** → Qdrant payload. You don't build this — the **embedding worker** chunks your source item into these. Carries scalar `region`, `party_id`, `source_type`, `authority_tier`, `citation_url/title`.

> Suggested tagging: `authority_tier` ∈ {authoritative, factual_record, self_reported, promotional} — e.g. votes ≈ `factual_record`, party self-descriptions ≈ `self_reported`, press releases ≈ `promotional`. This is meant to drive trust ranking later; refine the mapping if your source doesn't fit cleanly.

## 2. Add a new connector (the suggested shape)

You own **one file** + a test. Two shared files take a one-line append (coordinate so we don't collide).

1. **Create `ai-backend/src/ingestion/connectors/<your_source>.py`** subclassing `BaseConnector`. The proposed lifecycle is 8 methods — mirror `bundestag_votes.py` (HTML scrape) or `pledgetracker.py` (derived/external):
   ```
   read_watermark → write_watermark → discover → fetch →
   normalize → store_original → upsert_source_item → enqueue_embed
   ```
   - `discover(since)` — list external IDs newer than the watermark
   - `fetch(external_id)` — pull one raw payload (take an injectable `fetch_fn` so tests run offline)
   - `normalize(raw)` — return a valid `SourceItemRecord` with sensible tags
   - `store_original()` — call the shared `gcs.store_original()` helper; return the `gs://` URI
   - `enqueue_embed()` — set `vector_status=pending`; the worker handles embedding, not you
2. **Register it** in `registry.py` → a deferred-import factory + one line in `CONNECTOR_FACTORIES`.
3. **Add your `source_type`** enum member in `schemas.py` (the comment invites it: "Extend in Phase 3"). Reuse an existing `AuthorityTier` if one fits.
4. *(optional)* a `run-<source>` Makefile target copied from `run-bundestag-votes`.

**Try to leave these alone** (inherit / call only): `connector.py` (the ABC), `gcs.py`, `ids.py`, `worker.py`, `work_queue.py`, `retrieve.py`, `setup_collection.py`, `run.py`. If your source genuinely needs one of them to change, that's worth a group conversation -> it usually means the shared seam should evolve for everyone, which is fine.

**Guardrails we'd like to keep** (these are more load-bearing than the rest): idempotent runs (run twice → same count, via deterministic IDs from `ids.py`), watermark-resumable, and never read `users/{uid}` (GDPR Art. 9 — this one is non-negotiable).

## 3. Load data (run the pipeline locally)

```bash
# 0. one-time per shell
export FIRESTORE_EMULATOR_HOST=localhost:8081

# 1. bring up local stores (Qdrant + fake-gcs + Firestore/Storage emulators)
make stores-up

# 2. create the Qdrant collection + payload indexes (idempotent)
cd ai-backend && uv run python -m src.ingestion.setup_collection && cd ..

# 3. seed Firestore metadata (contexts, parties, sample source_items) — NOT the corpus
make seed-local

# 4. run YOUR connector: discover → fetch → normalize → GCS → source_item → enqueue
make run-<source>          # or: uv run python -m src.ingestion.run --connector <id>

# 5. run the embedding worker: picks up vector_status=pending → chunk → embed → Qdrant
make run-embed-worker
```

> The corpus (Qdrant) starts **empty** by design — local-only, no prod data this milestone. Your local corpus = whatever *your* connector emits from its fixtures. An empty Qdrant before step 4 is expected, not broken.

```bash
# unit test for your connector (inject a fetch_fn + a fixture JSON — no network)
cd ai-backend && uv run pytest tests/test_<your>_connector.py -x

# full backend suite + lint (CI gates)
make test-backend
```

Model your test on `tests/test_bundestag_connector.py`; drop a sample raw payload in `ai-backend/tests/fixtures/<your_source>_sample.json` (that file is connector **input**, not output).

**Idempotency check:** run your connector twice (step 4) → Qdrant point count shouldn't change.

## 6. Open questions & where the contract can flex

This is the part we most expect to evolve. Known soft spots:

**Is a `source_item` one item or an aggregate?** 
Raised re: votes — maybe it makes more sense to store *all of a party's votes on a topic* as one source item rather than one-per-vote. 
-> **The contract can mostly take this today**, because `SourceItemRecord` has no body and doesn't force one-row-per-vote -> you'd key `source_item_id`/`external_id` on `party_id + topic` and emit one chunk per underlying vote. Three things to settle first if we go this way:
- **`region` and `publish_date` are scalar on the source item.** An aggregate spanning several dates/regions loses fidelity at the item level (per-vote values can still live on each chunk).
- **No `topic_id` on the corpus records.** It exists on the matcher models but not on `SourceItemRecord`/`ChunkRecord`, so "filter the corpus by topic" isn't an indexed query yet. Aggregating *by topic* probably wants a `topic_id` field + payload index added.
- **Idempotency under updates.** When a new vote lands, the aggregate's content changes — keep `source_item_id` stable, upsert the doc, and make per-vote chunk IDs deterministic so old chunks aren't duplicated.

**Other things likely to bend as we go:** the `source_type` / `authority_tier` vocabularies (extend freely), chunking strategy per source, whether "one shape fits all" really holds for messier sources (transcripts, social), and the 8-step lifecycle if a source needs a genuinely different flow. The models are intentionally `frozen` + `extra="forbid"` so none of this changes silently, every amendment is visible and reviewed, which is the point.

**If you hit a wall:** don't force your source into a shape that hurts it. Note it here / raise it, and we evolve the contract. Better to change the common ground early than to diverge quietly.
