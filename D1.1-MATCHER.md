# MATCHER — Design Notes (wahl.chat V2)

> **Proposed thinking, not a built spec.** The scoring engine is deferred to a later milestone — the models in `ai-backend/src/matcher/schemas.py` (`Topic`, `Claim`, `Question`, `QuestionStancePair`) are matching-unit-only. This doc records *how we think the matcher can work* — and especially **how data from each source should (and shouldn't) feed it**, so nobody silently wires a source into the score in a way we'd later regret. Same spirit as the onboarding doc: these are defaults to push back on, not laws. If a source makes the boundary below awkward, that's a signal worth raising.

---

## 1. The core principle: comparability, not binary-ness

The matcher's job is to compute an *alignment* between a user and a party — a distance over positions. The property that makes that computable is **comparability**: every party has to take a position on the **same axis**.

It's tempting to assume matcher questions have to be yes/no. They don't. The real constraint is a **shared, bounded, symmetric axis** — a fixed question/thesis set on which every party is placed on the same scale. A 5-point agree↔disagree Likert works exactly as well as a binary one; binary is just the simplest case.

Votes give you this axis *for free*: every fraction "answers" every poll, on the same scale (yes / no / abstain), comparably across all parties. That's why votes *read* as binary — but it's the comparability, not the binary-ness, that's load-bearing. Explicit party surveys (the Wahl-O-Mat model) are the other clean way to get a comparable axis: the party states its own position on the exact thesis.

**Consequence:** a source is usable *for scoring* only if it places every party on a shared axis. A source can be enormously valuable to the product without satisfying that — it just feeds a different role (evidence / grounding), not the score.

---

## 2. Two roles, two stores: score vs evidence

| Role | What it is | Store | Comparable axis needed? |
|------|-----------|-------|--------------------------|
| **Score input** | the position that drives the alignment number | matcher (Firestore: `QuestionStancePair`) | **Yes** — shared axis across all parties |
| **Evidence / grounding** | the quote that explains/justifies a position to the user | corpus (Qdrant chunks) | No — free text is fine, often ideal |

The same source *can* feed both (votes do). But a source that only gives evidence (free-text Q&A) must **not** be folded into the score.

## 3. Source → matcher mapping

> Filling in abgeordnetenwatch now. Other sources get their own sub-section as we build their connectors.

### abgeordnetenwatch.de

**a) Polls + Votes → score input (comparable) ✅**

- A **poll** = a `Question` (the thesis). Its `field_topics` (Dip21 taxonomy) → `Topic`.
- Each **fraction's aggregated vote** → one `QuestionStancePair`: `party_id` = fraction→party slug, `stance` derived from the tally (yes→agree, no→disagree, abstain→neutral), `grounded_in = [the vote_record source_item_id]`, `topic_id` from the poll.
- This is a genuine comparable axis: every fraction in the legislature voted on the same poll.
- **Open decision — stance normalization for split/partial fractions:** a fraction is rarely unanimous (e.g. 225 yes / 4 abstain / 17 no_show on poll 3602). We need a rule — majority of *cast* votes? a threshold before "agree" vs "neutral"? how to treat high `no_show`? The SPEC should pin this.
- **Caveat to surface in the UI later:** votes reflect *party discipline* (party-/fraction-level), not necessarily an individual's conviction.

**b) Candidate Q&A (`/profile/<name>/fragen-antworten`, HTML scrape — no JSON API) → evidence only, NOT a score input**

- Free-text citizen-question + politician-answer. Lands in the **corpus** as `qa_transcript`, `self_reported` tier — excellent RAG grounding ("what does X actually say about Y," cited verbatim).
- **Deliberately excluded from the score this milestone.** Why it's unsafe as a scoring input:
  1. **Not a shared axis** — different citizens ask different politicians different questions; there's no common axis to compute a distance over.
  2. **Inference risk** — mapping prose → a stance label is an LLM judgement; when wrong you attribute a position the person doesn't hold, on Art. 9 special-category data, in a tool that influences votes. (Wahl-O-Mat uses explicit surveys precisely to avoid this.)
  3. **Selection / answer-rate bias** — many questions go unanswered, non-randomly; a score built on replies quietly encodes "who bothered to answer."
  4. **Level mismatch** — Q&A is per-candidate; the score is per-party. Aggregating is lossy, and where Q&A is the *only* signal (backbenchers) is exactly where inference risk peaks.
- **Allowed uses:** (i) grounding / citations in chat; (ii) an *explainability* layer that may surface an apparent stance **explicitly labelled as an inference, with the quote** — never silently summed into the number; (iii) **question mining** — the citizen questions themselves are a great source of "what people actually want to know" for the question bank / topic modelling / proactive chat.

**c) Election programs (Wahlprogramm PDFs) → evidence (corpus), `party_manifesto`.** Manifesto prose isn't a comparable axis; treat as grounding. (Likely owned by a dedicated manifesto connector — see onboarding §6.)

## 4. The boundary to hold this milestone

- **Score = comparable sources only** (votes now; explicit party surveys later if we ever run them).
- **Q&A and manifestos = evidence / grounding, never a scoring input** this milestone.
- The scoring engine itself stays deferred — `ai-backend/src/matcher/schemas.py` are matching-unit models only.
